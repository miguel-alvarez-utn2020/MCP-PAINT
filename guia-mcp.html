Guía interna · Model Context Protocol

Cómo funciona un MCP, explicado con un ejemplo que controla Paint

Un MCP le da a Claude manos para actuar sobre programas y servicios fuera de sí mismo. Acá está el concepto, las piezas clave y un caso real que construimos: un servidor que abre Paint y dibuja en el lienzo.

Ejemplo: Paint MCP Stack: Python · FastMCP Cliente: Claude Code

Qué es

Un protocolo para que la IA use herramientas externas

MCP (Model Context Protocol) es un estándar abierto que define cómo un modelo de IA (el cliente) puede descubrir y usar capacidades que viven en un programa aparte (el servidor). En vez de que cada integración se invente su propia forma de hablar con Claude, todas hablan el mismo idioma.

La analogía útil: el MCP es como un puerto USB para la IA. Claude trae el "enchufe"; vos construís un dispositivo (el servidor) que expone funciones concretas. Mientras respete el protocolo, Claude lo puede usar sin saber nada de cómo está hecho por dentro.

La idea central: Claude por sí solo razona y escribe texto. Un MCP le agrega acciones: leer una base de datos, llamar una API, mover archivos… o, en nuestro caso, mover el mouse y dibujar en Paint.

El flujo

Qué pasa cuando le pedís "dibujá un cuadrado"

El cliente lanza al servidor como un subproceso y se hablan por mensajes (JSON-RPC sobre la entrada/salida estándar). Claude lee las tools disponibles, elige cuál llamar y con qué argumentos, y el servidor ejecuta la acción real.

Las piezas

Tres partes y nada más

1

El servidor

Un programa (en nuestro caso server.py) que arranca, se anuncia y queda esperando llamadas. Acá usamos FastMCP, el SDK oficial de MCP para Python, que reduce el servidor a unas pocas líneas.

2

Las tools

Cada acción es una función decorada que el servidor publica. Tres cosas la definen: un nombre, una descripción (lo que Claude lee para decidir cuándo usarla) y sus parámetros tipados. El texto de la descripción importa tanto como el código.

3

La configuración del cliente

Un archivo .mcp.json le dice a Claude Code cómo lanzar el servidor (qué comando correr y en qué carpeta). Con eso el servidor aparece en /mcp y sus tools quedan disponibles.

Anatomía de una tool

Una función + una buena descripción

Así se ve una tool real de nuestro servidor. El decorador @mcp.tool() la publica; el docstring es literalmente lo que Claude lee para saber qué hace; y las anotaciones de tipo (int) se convierten en el esquema de argumentos que Claude debe completar.

server.py
@mcp.tool()
def draw_rectangle(x: int, y: int, width: int, height: int) -> str:
    """Dibuja un rectángulo con esquina superior izquierda en (x,y).

    Se dibuja como 4 líneas conectadas, independiente de
    la herramienta activa de Paint."""
    win = _focus_paint()        # trae Paint al frente
    _begin_pencil(win)          # elige el lápiz
    corners = [(x, y), (x+width, y), (x+width, y+height),
               (x, y+height), (x, y)]
    _stroke(win, corners)       # traza los 4 lados
    return f"Rectángulo dibujado en ({x},{y}) de {width}x{height}."
Clave que sorprende a todos: Claude no "ve" tu código. Elige qué tool usar leyendo el nombre y la descripción. Una descripción vaga = Claude no la usa bien. Escribir buenas descripciones es parte del trabajo de hacer un MCP.

El ejemplo

Paint MCP: siete tools para dibujar

Paint no tiene una API para programarlo. Así que el servidor lo controla por automatización de GUI: literalmente mueve el mouse real y hace clics. Las coordenadas que reciben las tools son relativas al lienzo, y el servidor las traduce a la pantalla.

ToolQué hace
open_paintAbre Paint, lo maximiza y lo enfoca
get_canvas_infoDevuelve la región del lienzo y el estado de calibración
draw_lineUna línea recta entre dos puntos
draw_rectangleUn rectángulo (4 líneas conectadas)
draw_polylineUn trazo libre por una lista de puntos (curvas, formas)
clear_canvasLimpia el lienzo
save_canvasGuarda el lienzo como PNG

Lo que dibujó, de verdad

Todo esto lo trazó el servidor solo, moviendo el mouse. Las curvas se logran dando muchos puntos seguidos; los picos rectos salen naturales.

Lo que aprendimos peleándola

El protocolo es lo fácil; el mundo real es lo difícil

Levantar el servidor MCP fue rápido. Lo que llevó trabajo fue que Paint realmente dibujara. Estas trabas son la parte más instructiva del ejemplo:

Ventana equivocada

Buscar la ventana por título fallaba: VS Code abierto en la carpeta "MCP-TEST-Paint" también tenía "paint" en el título. Solución: ubicar la ventana por su proceso (mspaint.exe).

El arrastre no pintaba

Mover el mouse con el botón apretado dejaba solo un punto, y el primer trazo tras tocar el menú se perdía. Solución: seleccionar el lápiz, un arrastre de "calentamiento", y trazar cada segmento con dragTo.

Pantalla al 125%

El proceso del servidor veía la pantalla "escalada" y todo caía corrido. Solución: declarar el proceso DPI-aware al arrancar.

Coordenadas frágiles

Cambiar de monitor o resolución descalibraba todo. Solución: auto-calibración — detectar el lienzo por su zona blanca y ubicar el lápiz por reconocimiento de imagen.

La moraleja para el equipo: un MCP que toca el mundo real (GUI, hardware, sistemas externos) hereda toda la fragilidad de ese mundo. El valor está en encapsular esa complejidad detrás de tools simples y bien descritas.

Cómo armar el tuyo

De cero a un MCP funcionando

  1. Elegí qué acción exponer¿Qué querés que Claude pueda hacer que hoy no puede? Esa es tu primera tool.
  2. Elegí lenguaje y SDKPython con FastMCP o TypeScript con el SDK oficial. Nosotros usamos Python por la automatización de GUI en Windows.
  3. Escribí las toolsUna función por acción, con nombre claro, descripción explícita y parámetros tipados. La descripción es la "interfaz" que ve Claude.
  4. Registrá el servidor en el clienteUn .mcp.json que diga cómo lanzarlo. Reiniciá/reconectá y verificá con /mcp.
  5. Probá e iteráPedile a Claude que use las tools, observá qué falla, afiná descripciones y maneja los casos del mundo real.

Criterio

Cuándo conviene (y cuándo no)

Tiene sentido un MCP

  • Claude necesita actuar sobre algo externo: una API, una base de datos, archivos, una app.
  • Es una capacidad reutilizable que vas a querer en varias conversaciones o proyectos.
  • Querés estandarizar el acceso para todo el equipo.

Quizás no haga falta

  • Es una tarea única que un script suelto resuelve.
  • El sistema externo ya tiene una integración mejor (un plugin, un connector).
  • Solo necesitás que Claude razone sobre texto, sin ejecutar acciones.
Una nota de seguridad: las tools de un MCP ejecutan acciones reales en tu máquina. Por eso el cliente pide permiso antes de cada llamada; en el ejemplo configuramos una lista de permitidos para no interrumpir el dibujo.

Escalado de calidad

De dibujo a ojo a reproducción por visión artificial

El MCP siempre fue el mismo — las tools draw_polyline y save_canvas no cambiaron. Lo que escalamos fue la calidad de las instrucciones que le pasamos. Este es el recorrido de tres versiones de Goku:

Versión 1 — Caricatura manual
21 trazos escritos a mano. Formas básicas estimadas a ojo: círculo para la cabeza, triángulos para el pelo, líneas simples. Sin referencia, sin medición.
Técnica Coordenadas estimadas → código
Versión 2 — Boceto manual sobre referencia
21 trazos estimados mirando el boceto. Se agregó un espacio de diseño (564×752) y transformación de escala, pero las coordenadas siguen siendo estimaciones manuales punto a punto.
Técnica Mirar imagen → estimar (x,y) a mano
Versión 3 — Extracción por OpenCV
249 trazos extraídos del boceto real. El algoritmo lee los píxeles, detecta bordes con Canny, extrae contornos y los convierte en polylines. El resultado incluye el rayado y los picos exactos del original.
Técnica OpenCV → Canny → findContours → approxPolyDP

Por qué mejoró tanto la v3

La calidad no depende de las "habilidades de dibujo" de quien programa — depende de qué tan precisas son las coordenadas que le das al sistema. Con visión artificial, las coordenadas vienen directamente de los píxeles del boceto original:

El MCP como “brazo”, no como “cerebro”

El servidor server.py es el brazo: ejecuta trazos con el mouse. La evolución de calidad viene de qué información le pasás. Lo mismo aplica a cualquier MCP: cuanto más precisas y estructuradas sean las instrucciones que llegan desde el cliente, mejor el resultado.

El protocolo no cambia — solo cambia el pipeline que genera las coordenadas. Podría seguir escalando: vectorización automática, separación por capas, reconocimiento de estilos. El MCP es la base estable; la inteligencia crece alrededor.
